## 1. Что сделал

В рамках лабораторной работы разработан полноценный автономный **ReAct-агент на чистом Python** (без использования высокоуровневых библиотек LangChain, LangGraph и т.п.).

### 1.1. Архитектура и схема ReAct-цикла

```
             ┌────────────────────────────────────────────────────────┐
             │                     Вопрос пользователя                │
             └───────────────────────────┬────────────────────────────┘
                                         ▼
                                ┌─────────────────┐
                  ┌────────────▶│    LLM / Модель │◀────────────────┐
                  │             └────────┬────────┘                 │
                  │                      │ Thought                  │
                  │                      ▼                          │
                  │        ┌───────────────────────────┐            │
                  │        │          Парсер           │            │
                  │        └─────────────┬─────────────┘            │
                  │                      │                          │
        Final Answer?              Action?│                          │ Ошибка формата?
        ┌─────────┴─────────┐            ▼                          │
        │ Завершить цикл,   │   ┌─────────────────┐                 │
        │ вернуть ответ     │   │   tools.py:     │                 │
        └───────────────────┘   │ - calculator    │                 │
                                │ - text_search   │                 │
                                └────────┬────────┘                 │
                                         │ Observation              │
                                         └──────────────────────────┘
                                      (добавляется в историю)
```

### 1.2. Ключевые проектные решения

1. **Безопасный калькулятор (`calculator` в `tools.py`)**:
   - Реализован на базе модуля абстрактного синтаксического дерева (`ast`), исключая использование уязвимого `eval()` (защита от OWASP LLM06: Excessive Agency и Prompt Injection).
   - Поддерживает только разрешённые узлы чисел и операторов (`+`, `-`, `*`, `/`, `%`, `**`, унарные плюсы и минусы).
   - Встроена защита от DoS-атак через чрезмерные степени (`abs(power) > 100`) и обработка деления на ноль (`ZeroDivisionError`).
   - Возвращает ошибки в виде текстового описания (`"Ошибка: ..."`), передаваемого агенту как `Observation`, что позволяет модели исправиться без падения программы.

2. **Поиск по текстовым документам (`text_search` в `tools.py`)**:
   - Полнотекстовый поиск по 4 регламентам компании в папке `docs/`: `hr_policy.txt`, `travel_policy.txt`, `bonuses_and_compensation.txt`, `training_policy.txt`.
   - Реализована нормализация и псевдо-стемминг для русского языка (префикс 6 букв для длинных слов и отсечение гласных окончаний), что позволяет успешно сопоставлять формы слов (например, «командировка», «командировки», «командировочные»).
   - Скоринг абзацев по числу совпадений, сортировка по убыванию релевантности и возврат top-k фрагментов с ссылкой на источник `[файл, абзац i]`.
   - При отсутствии совпадений возвращается подсказка: *«По вашему запросу ничего не найдено... Попробуйте переформулировать ключевые слова»*.

3. **Системный промпт и парсер (`agent.py`)**:
   - Строгий интерфейс ReAct (`Thought:`, `Action:`, `Action Input:`, `Final Answer:`).
   - Предотвращение галлюцинаций через `stop=["Observation:"]` в API и программную обрезку текста по `"Observation:"` в парсере.
   - Корректная обработка порядка совпадений регулярок (что раньше встретилось — финал или вызов действия).
   - Защита от несуществующих инструментов и синтаксических сбоев формата: агент получает поясняющий `Observation` и может скорректировать траекторию.

4. **Журнал трассировки шагов (`agent_log.jsonl`)**:
   - Формат JSON Lines (одна запись на строку) с полями: `ts`, `run_id`, `step`, `event` (`start`, `step`, `final`, `max_steps_reached`), `llm_output`, `action`, `action_input`, `observation`, `tool_ok`, `latency_s`, `usage` (`prompt_tokens`, `completion_tokens`, `total_tokens`).
   - Поддержка анализа через библиотеку `pandas` в `analyze_logs.py`.

5. **Гибкость сред исполнения (Groq / Ollama / Mock LLM)**:
   - Поддержка облачного Groq (`openai/gpt-oss-20b`), локальной Ollama и детерминированного генератора `make_mock_llm` для воспроизводимых unit-тестов.

## 4. Продвинутая часть (Бонусные задания, +10 баллов)

В файле `advanced_features.py` реализованы два ключевых паттерна продвинутых агентных систем:

### 4.1. Паттерн Reflexion (Вариант C, Shinn et al., NeurIPS 2023)
* **Архитектура:**
  - **Actor:** ReAct-агент выполняет шаги.
  - **Evaluator:** автоматический валидатор проверяет, содержит ли ответ числовое решение (или требуемые сущности).
  - **Self-Reflection Generator:** при отрицательном вердикте формулирует текстовую критику ошибки.
  - **Episodic Memory:** вербальная критика помещается в контекст, и агент запускает вторую попытку (Trial 2).
* **Результат демонстрации:**
  - *Попытка 1:* Агент ответил общей фразой без вычислений: *«Суточные выплачиваются по установленной ставке...»*. Валидатор отклонил ответ (`False`).
  - *Генерация рефлексии:* *«В попытке 1 была допущена ошибка: Ответ не содержит конкретного числа. В следующей попытке необходимо обязательно использовать calculator и указать число»*.
  - *Попытка 2:* Агент учёл рефлексию, вызвал `calculator`, получил `7500` и выдал: *«За 5 дней командировки сотруднику полагается 7500 сом суточных»*. Валидация пройдена успешно (`True`).

### 4.2. Паттерн Human-in-the-Loop (Вариант D)
* Добавлен инструмент `ask_human(question)`.
* При неоднозначном запросе (*«Сколько суточных мне положено?»*) агент не угадывает, а запрашивает уточнение у человека (*«Уточните: поездка по стране или за рубеж, и сколько дней?»*).
* Получив ответ пользователя, агент безошибочно рассчитывает результат.

## 5. Что усвоил

1. Паттерн ReAct превращает языковую модель из простого генератора текста в рассуждающего координатора, динамически принимающего решения на каждом шаге на основе результатов внешних действий.
2. Языковая модель сама по себе не выполняет код и не ходит в базы данных — она лишь генерирует намерения вызова в виде текста. Вся безопасность, валидация аргументов, защита от Prompt Injection и гарантия завершения циклов лежат на программном коде разработчика.
3. Качественная обработка ошибок в инструментах (возврат строки ошибки вместо выброса исключения) является фундаментом устойчивости агента: модель воспринимает ошибку как новое наблюдение и способна самостоятельно переформулировать запрос или скорректировать параметры.

## 7. Ответы на контрольные вопросы (Разделы 13–14)

### 1. Чем агент отличается от workflow по определению Anthropic? Когда агент не нужен?
В **workflow** последовательность шагов и маршруты ветвления жестко зафиксированы разработчиком в коде (детерминированный пайплайн). В **агенте** LLM самостоятельно и динамически определяет последовательность шагов, выбирает инструменты и решает, когда закончить работу. Агент не нужен, если задачу можно решить одним вызовом LLM или простым жестким скриптом: workflow дешевле, быстрее, предсказуемее и не накапливает ошибки по цепочке.

### 2. Из каких компонентов состоит LLM-агент по формуле Лилиан Венг?
Формула: **Агент = LLM + Планирование + Память + Использование инструментов**. LLM выполняет роль «мозга»; планирование отвечает за декомпозицию задач и самокритику; память (краткосрочная и долгосрочная) хранит контекст и предыдущий опыт; инструменты обеспечивают взаимодействие с внешним миром и доступ к актуальным данным.

### 3. Из каких элементов состоит шаг ReAct и кто формирует каждый из них?
- **Thought (мысль)** — генерирует модель (рассуждение о текущей ситуации и следующем действии).
- **Action и Action Input (действие и аргументы)** — генерирует модель (декларация намерения вызвать конкретный инструмент).
- **Observation (наблюдение)** — формирует программный код среды после реального выполнения функции инструмента.
- **Final Answer (итоговый ответ)** — генерирует модель, когда собрано достаточно информации; это завершает цикл.

### 4. Какие проблемы Chain-of-Thought решает ReAct и какие результаты показала оригинальная статья?
Chain-of-Thought опирается исключительно на внутреннюю статическую память модели, что приводит к галлюцинациям и накоплению ошибок при длинных рассуждениях. ReAct решает эту проблему за счет получения достоверных фактов из внешних источников через действия. В статье Yao et al. (ICLR 2023) на бенчмарках ALFWorld и WebShop ReAct превзошел методы имитационного обучения и RL на 34 и 10 процентных пунктов успешности всего с 1–2 примерами в промпте.

### 5. Зачем в лабораторной используется параметр `stop=["Observation:"]` и обрезка ответа модели по этой строке?
Модели часто обучаются на примерах ReAct-диалогов и имеют свойство продолжать генерацию, выдумывая псевдо-результаты инструмента (галлюцинируя за среду). Параметр `stop` принудительно останавливает генерацию в API на токене `Observation:`, а обрезка в коде парсера служит дополнительной гарантией, если провайдер не поддержал стоп-последовательность.

### 6. Зачем ограничивать число шагов агента (`max_steps`) и что должен делать агент при исчерпании лимита?
Без лимита агент может войти в бесконечный цикл (например, бесконечно переформулировать неудачный поисковый запрос), исчерпав бюджет токенов и заблокировав сервис. При исчерпании лимита агент обязан корректно завершить работу, вернуть понятное сообщение о невозможности найти ответ за отведенное число шагов и зафиксировать событие в логе.

### 7. Как устроен паттерн Plan-and-Execute и в каких задачах он выгоднее ReAct?
Сначала LLM-планировщик составляет структурированный план из всех этапов задачи, затем исполнитель выполняет их (независимые шаги могут запускаться параллельно, как в ReWOO), а модуль перепланирования сверяет прогресс. Паттерн выгоднее ReAct в длинных многоэтапных задачах с понятной структурой, так как снижает число дорогих вызовов большой модели. Главный риск — устаревание плана при динамических изменениях среды.

### 8. Из каких компонентов состоит Reflexion и при каком условии его имеет смысл применять?
Состоит из **Actor** (исполнитель), **Evaluator** (оценщик результата) и модуля **Self-Reflection** (генератор текстовой критики), сохраняющего выводы в эпизодическую память для следующих попыток (Shinn et al., NeurIPS 2023: 91% pass@1 на HumanEval против 80% у GPT-4). Применять имеет смысл, когда результат можно надежно проверить автоматически (тесты, SQL, JSON-схема), а качество критичнее затрат на дополнительные попытки.

### 9. Сравните in-context, векторную и структурированную (БД) память агента.
- **In-context:** история диалога прямо в системном/пользовательском запросе; доступна мгновенно, но ограничена контекстным окном и удорожает каждый шаг.
- **Векторная память:** хранит эмбеддинги неструктурированных текстов в векторных БД (Chroma, Qdrant) с поиском по сходству top-k; риск — нерелевантные или устаревшие фрагменты.
- **Структурированная память:** реляционные/NoSQL БД (PostgreSQL, Redis), хранящие точные факты (балансы, статусы, транзакции); требует точных SQL/API запросов через инструменты.

### 10. Что такое эффект «Lost in the Middle» и что он означает для проектирования памяти агента?
Исследование Liu et al. (2023) показало, что LLM значительно лучше извлекают информацию из начала и самого конца переданного контекста, тогда как данные в середине окна внимания часто игнорируются или теряются. Для проектирования памяти это означает: нельзя «сваливать всё подряд в контекст» — необходимо сжимать историю, суммаризировать прошлые наблюдения и размещать критические инструкции ближе к границам промпта.

### 11. Опишите механику нативного function calling. Кто выполняет функцию и от чего зависит выбор инструмента?
Разработчик описывает инструменты через JSON Schema в запросе к API. Модель в ответ генерирует не обычный текст, а валидный JSON с именем функции и аргументами. Саму функцию всегда выполняет код приложения, после чего отправляет результат обратно модели сообщением с ролью `tool`. На выбор инструмента влияют четкость описания (когда вызывать, а когда нет), понятные имена параметров и системные правила.

### 12. Какие значения параметра tool_choice есть в Anthropic API и как принудительный вызов помогает извлекать структурированные данные?
Значения: `auto` (модель решает сама), `any` (обязана вызвать хотя бы один инструмент), `tool` (обязана вызвать конкретный указанный инструмент), `none` (вызовы запрещены). Принудительный вызов конкретного инструмента с жесткой JSON-схемой гарантирует, что модель вернет валидный структурированный JSON нужного формата без лишнего текста вокруг.

### 13. Чем текстовый ReAct из лабораторной отличается от нативного function calling? Почему в работе выбран текстовый вариант?
В текстовом ReAct вызовы передаются обычным текстом по конвенции (`Action:` / `Action Input:`) и разбираются регулярными выражениями — это работает с любой instruct-моделью, но подвержено синтаксическим сбоям. В нативном function calling разбор идет на уровне API через структурированные токены. Текстовый вариант выбран в учебных целях, чтобы студенты наглядно увидели внутреннюю «кухню» агента: промптинг, парсинг, управление циклом и механизм самоисправления.

### 14. Почему калькулятор на eval() опасен и как защищён калькулятор в лабораторной? Какой риск OWASP с этим связан?
Строка для вычисления может быть сгенерирована моделью под влиянием скрытой инъекции из найденных документов (Prompt Injection), что при `eval()` приведет к выполнению произвольного системного кода (`__import__('os').system(...)`). Калькулятор защищен парсингом в AST-дерево с белым списком арифметических операторов и ограничением на показатель степени. Это закрывает риск **OWASP LLM06: Excessive Agency (чрезмерная автономность)**.

### 15. Почему инструменты агента возвращают ошибку текстом, а не выбрасывают исключение, и зачем каждая такая ошибка записывается в журнал?
Выброс исключения аварийно завершил бы всю программу. Возврат ошибки текстом превращает её в `Observation`: языковая модель видит причину неудачи (неправильный инструмент, ошибка деления на ноль) и способна скорректировать свои действия. Запись ошибок в журнал JSONL позволяет проводить аудит сбоев, вычислять показатель `tool_ok` и отслеживать качество работы агента в production.
